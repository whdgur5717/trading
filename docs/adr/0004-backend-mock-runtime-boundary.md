# 개발 mock 실행 경계

외부 API handler와 응답 fixture가 `test/support`에 있으면 테스트 전용 자원처럼
보이지만, 같은 대체 서버는 로컬에서 백엔드 전체를 실행할 때도 필요하다. 테스트용
앱 생성 함수와 개발용 진입점이 각각 Nest 애플리케이션을 조립하면 실제 mock 실행
구성이 둘로 갈라지고, 한쪽에서 추가한 모듈이나 초기화가 다른 쪽에 반영되지 않을 수
있다.

개발 mock 환경은 `src/mock`이 소유한다. `MockModule`은 실제 애플리케이션 모듈에
외부 연동 대체와 백엔드 API 응답 override를 결합하는 유일한 구성이다.
`main.mock.ts`는 이 모듈을 실행하고, 전체 mock 환경이 필요한 e2e 테스트도 별도의
앱 조립 함수를 만들지 않고 같은 모듈을 실행한다.

외부 연동 대체와 백엔드 응답 override는 하나의 기능으로 합치지 않는다.
`ExternalModule`은 KIS, 금융위원회, OpenDART로 나가는 REST 요청과 KIS WebSocket
연결을 로컬 응답으로 바꾼다. `OverrideModule`은 mock 앱으로 들어온 요청에 저장된
응답이 있으면 컨트롤러보다 먼저 반환한다. `MockRuntime`은 두 기능의 상태와 열린
연결을 함께 초기화하지만, 응답을 선택하는 규칙까지 공유하지 않는다.

일반 실행은 `main.ts`와 실제 애플리케이션 모듈을 사용하며 mock 모듈을 불러오지
않는다. 운영 빌드는 `src/mock`과 `main.mock.ts`를 제외한다. mock 실행에는 생성된
외부 REST handler가 필요하므로 별도의 TypeScript 설정으로 `src`와 외부 OpenAPI
생성물을 함께 컴파일한다. 테스트는 mock 실행 구성을 사용할 수 있지만, 애플리케이션
코드는 `test` 아래의 파일을 import하지 않는다.

이 결정은 외부 API 대체를 e2e 테스트의 보조 수단으로만 규정했던 이전 내용을
대체한다. mock 구현은 개발 실행 코드이지만 운영 산출물은 아니며, 테스트 폴더에는
테스트 케이스와 테스트에서만 필요한 코드만 둔다.
