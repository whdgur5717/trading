# 코드가 따르는 구조를 읽기

코드는 더 큰 실행 방식 안에 놓인다. 프레임워크가 호출 지점을 정하기도 하고, 여러 모듈이 반복해서 협력하는 방식이 생기기도 하며, 한 함수 안에서는 주 흐름과 그 흐름에 딸린 세부 단계가 생긴다.

파일, 폴더, 함수와 변수의 배치는 이런 관계를 독자가 찾는 데 도움을 줘야 한다. 요구사항의 명사나 구현 중 떠오른 동작은 이름을 만드는 재료가 될 수 있다. 그 이름들이 실제 역할과 소유 관계를 가릴 때 구조를 다시 살펴볼 이유가 생긴다.

## 어디에서 구조를 찾는가

| 범위 | 코드에서 확인할 것                                                |
| ---- | ----------------------------------------------------------------- |
| 바깥 | 이 코드를 호출하는 프레임워크, 프로토콜, 상위 모듈과 그 확장 지점 |
| 사이 | 여러 부분에서 반복되는 역할, 실행 순서, 의존 방향과 변경 경로     |
| 안   | 주 진입점과 핵심 흐름, 특정 단계에만 속한 세부 구현               |

세 범위는 한 코드 안에서 겹친다. 바깥의 실행 방식은 모듈의 역할을 정하고, 모듈 내부의 구성은 그 역할을 수행하는 과정을 보여준다.

```text
코드가 참여하는 실행 방식
└── 모듈이 맡은 역할
    └── 역할을 수행하는 주 흐름
        └── 각 단계에 속한 세부 구현
```

물리적인 파일 트리는 이 관계를 여러 방식으로 표현할 수 있다. 독자가 진입점, 역할, 소유 관계를 파악하기 위해 호출 그래프 전체를 다시 조립해야 한다면 현재 배치가 관계를 충분히 설명하는지 확인한다.

## 관계가 평평해지는 경우

구현 단계마다 이름을 붙여 같은 높이의 파일이나 최상위 함수로 올리면, 실제 호출 관계에 있던 위계가 소스에서 약해질 수 있다.

- 파일의 진입점이 여러 보조 선언 사이에 묻혀 있다.
- 한 곳에서만 쓰이는 세부 함수들이 서로 독립된 기능처럼 배치되어 있다.
- 보조 함수 이름마다 부모 기능의 이름이 반복된다.
- 프레임워크와 맞닿는 연결부를 찾은 뒤에도 자체 로직이 어느 호출 지점에서 실행되는지 계속 추적해야 한다.
- 기능별 파일들이 내부에서 같은 역할과 호출 순서를 반복한다.
- 하나의 기반 변경이 독립적으로 보이는 여러 파일에 같은 형태로 전파된다.

각 현상은 조사할 위치를 알려준다. 실제 재사용, 독립된 소유권, 서로 다른 변경 이유가 확인되면 같은 배치도 그 관계를 정확히 표현할 수 있다.

## 판단하기

코드의 이름에서 얻은 인상을 실제 호출과 변경 근거로 검증한다. 다음 순서로 현재 구조와 실제 관계를 비교한다.

1. 누가 이 코드를 호출하고 무엇을 기대하는지 확인한다.
2. 진입점에서 결과까지 실행 흐름을 따라간다.
3. 독립적으로 쓰이거나 변경되는 부분과 특정 흐름에만 속한 부분을 구분한다. 변경 관계는 실제 이력, 소유권 또는 계약으로 확인하고, 코드 모양에서 예상한 변경 가능성과 섞지 않는다.
4. 현재 파일과 선언 배치가 이 관계를 얼마나 보여주는지 확인한다.
5. 독자가 구조에서 얻지 못해 다시 복원해야 하는 정보를 적는다.

판단 결과에는 다음 내용이 이어져야 한다.

```text
코드에서 확인한 실제 관계
→ 현재 배치가 강조하는 관계
→ 배치에서 흐려진 관계
→ 독해와 변경에 생기는 구체적인 영향
```

예를 들어 헬퍼의 수는 조사할 위치를 알려준다. 모든 헬퍼가 하나의 진입점에서만 사용되고 독립된 변경 이유도 없는데 같은 높이로 배치되어 있다면, 주 흐름과 세부 구현의 소유 관계가 흐려졌다는 근거가 생긴다.

## 진단 이후

같은 진단에서도 가능한 구성은 여러 가지다. 소스의 읽는 순서만 바꿀 수 있고, 세부 동작을 주 흐름 가까이에 둘 수 있으며, 의미 있는 단계끼리 묶거나 독립된 판단을 별도 모듈로 둘 수도 있다.

재구성은 각 대안이 실제 관계를 얼마나 선명하게 보여주는지, 그 과정에서 새로운 개념을 얼마나 추가하는지 비교해서 결정한다. 구조적 어긋남을 발견한 시점에는 특정 함수 수, 파일 트리 또는 디자인 패턴까지 확정할 근거가 아직 없을 수 있다.

## Examples

> 아래 사례는 판단 과정을 보여준다. 코드 형태와 해결 방향은 각 사례의 맥락에만 속한다.

### 파일 내부의 파싱 흐름

```ts
const splitHeaderForRecord = () => {}
const splitBodyForRecord = () => {}
const parseBodyLineForRecord = () => {}
const validateFieldForRecord = () => {}

export const parseRecord = () => {}
```

`parseRecord`만 외부에서 사용되고 나머지 함수가 그 실행 경로에만 속한다면, 호출 관계에는 `parseRecord`와 그 세부 단계라는 위계가 있다. 현재 배치는 다섯 함수를 같은 높이로 보여주며, 반복되는 `ForRecord`가 소유 관계를 이름으로 보충한다.

각 함수가 다른 파서에서도 사용되거나 독립된 문법 규칙을 표현한다면 최상위 선언에는 별도의 근거가 생긴다. 같은 코드 모양도 실제 소유 관계에 따라 다르게 판단된다.

### ESLint rule

[ESLint rule](https://eslint.org/docs/latest/extend/custom-rules)은 `meta`, `create(context)`, `create`가 반환하는 AST visitor를 통해 실행된다. 이 구조는 자체 검사 로직이 ESLint에 적용되는 경로를 제공한다.

파일 대부분이 자체 로직을 잘게 나눈 최상위 함수로 채워지고 rule 객체가 마지막의 얇은 연결부로 남으면, 독자는 visitor의 호출 시점과 검사·보고의 연결을 다시 추적하게 된다. 자체 판단이 다른 환경에서도 사용되는 독립된 정책이라면 별도 모듈이 그 관계를 더 잘 보여줄 수 있다. 이 경우에는 rule과 정책이 연결되는 지점이 읽혀야 한다.

### 기능별 디렉터리

기능별 파일은 기능마다 소유권과 변경 이유가 다를 때 그 관계를 잘 보여준다. 동시에 모든 기능 파일이 같은 역할과 호출 순서를 반복하고, 기반 동작의 변경이 매번 함께 전파될 수도 있다.

이 경우 구조에는 기능 경계와 반복되는 협력 방식이라는 두 축이 존재한다. 리뷰에서는 두 축의 근거를 모두 밝힌다. 어느 축을 파일이나 폴더로 표현할지는 실제 변경 경로와 의존 관계를 더 살핀 뒤 결정한다.
